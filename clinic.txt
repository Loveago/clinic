# MASTER BUILD SPECIFICATION
## Integrated Clinic & Nursing Training School Digital Platform

**Powered by:** Crazy Tech Enterprise  
**Project Type:** Full-Stack Web Application  
**Frontend:** Next.js, React, TypeScript  
**Backend:** Node.js, NestJS, TypeScript  
**Database:** PostgreSQL  
**ORM:** Prisma  
**Architecture:** Modular, API-driven, multi-portal application

---

# 1. PROJECT OBJECTIVE

Build a complete, modern, secure and scalable digital platform for a healthcare clinic that also operates a nursing training institution.

The system must combine three major products:

1. A professional public-facing clinic website.
2. A nursing training school website.
3. A comprehensive school management and e-learning system.

The system must support different users, administrative roles, academic workflows, online payments, course management, examinations, student performance tracking and institutional reporting.

This is a real production application, not a demonstration project.

**Important development instructions:**

- Build working features, not static mockups.
- All forms must connect to real backend endpoints.
- All dashboards must display actual database information.
- All buttons and actions must work.
- Authentication and authorization must be implemented properly.
- Do not use fake data as a substitute for real functionality.
- Do not leave placeholder pages or unfinished modules.
- Build reusable components and maintainable architecture.
- Make the platform responsive, particularly on mobile devices.
- Prioritize functionality, security and maintainability alongside visual quality.

- Node.js.
- NestJS.
- TypeScript.

- Prisma ORM.
- PostgreSQL.
- JWT-based authentication with secure refresh-token handling.
- Role-based access control.
- Swagger/OpenAPI API documentation.

## Supporting Infrastructure

- PostgreSQL database.

# 26. SECURITY REQUIREMENTS

Security is a core requirement.

Implement:

- Password hashing using Argon2id or an equivalent secure algorithm.
- Secure HTTP-only cookies for authentication.
- Short-lived access tokens and protected refresh-token rotation.
- Backend-enforced role-based access control.
- Input validation using DTOs and Zod where appropriate.
- Protection against SQL injection.
- Rate limiting on sensitive endpoints.
- CSRF protection where applicable.
- Secure file upload validation.
- File type and size restrictions.
- Secure password reset.
- Login attempt protection.
- Audit logs for sensitive administrative actions.
- Database backups.
- Secure environment variable management.
- HTTPS in production.
- Restricted administrative access.

Use least-privilege permissions.

Student records, financial information and any future health-related information must be protected appropriately.

Design with Ghana's Data Protection Act, 2012 (Act 843) and applicable institutional requirements in mind. The institution should review its data protection, consent, retention and privacy obligations before launch.

Do not collect or expose patient medical records as part of the initial clinic website.

- White for clean content surfaces.
- Soft neutral backgrounds.
- Restrained mint and green accents.

### Typography

Typography must look deliberate and professionally selected.

- Use a contemporary sans-serif font family or a carefully selected font pairing.
- Establish a consistent typography scale.
- Use strong display headings for important sections.
- Use readable body text.
- Maintain consistent font weights and line heights.
- Avoid random font sizes and inconsistent typography.

Headings should have character and hierarchy without being unnecessarily oversized.

### Spacing and layout

Spacing is extremely important.

- Use generous but controlled whitespace.
- Maintain consistent alignment.
- Use a deliberate grid system.
- Avoid cramped content.
- Avoid enormous empty sections.
- Establish consistent content widths.
- Use proper spacing between headings, paragraphs, cards and actions.

The interface should feel carefully composed rather than automatically generated.

### Photography and imagery

Use high-quality, relevant photography.

Appropriate imagery includes:

- Healthcare professionals.
- Clinical environments.
- Nursing students.
- Medical training.
- Healthcare facilities.
- Educational environments.

Images must support the content.

### Cards, borders and surfaces

Use:

- Refined card layouts.
- Subtle borders.
- Restrained shadows.
- Carefully chosen corner radii.
- Consistent spacing.
- Clear content separation.

## 27.7. Desktop, tablet and mobile requirements

Desktop and mobile are equally important.

Design them as separate experiences that belong to the same product.

Tablet layouts must also be considered.

### Desktop

- Use screen width intelligently.
- Establish clear content grids.
- Use sensible maximum content widths.
- Use sidebars and multi-column layouts only when they improve navigation or information scanning.
- Avoid overly wide text lines.
- Avoid oversized empty regions.
- Ensure tables, dashboards and complex workflows remain easy to scan.

### Tablet

- Adapt navigation and columns intentionally.
- Reflow cards and data layouts before they become cramped.
- Keep forms and actions accessible.
- Do not simply shrink desktop components.

### Mobile

- Design mobile-first, not as a compressed desktop layout.
- Recompose hero sections vertically.
- Use readable text and intentional image crops.
- Use compact, accessible navigation.
- Stack service and programme content cleanly.
- Make forms comfortable to complete.
- Use appropriate input sizes and clear validation messages.
- Use a usable mobile menu or bottom navigation for authenticated portals where appropriate.
- Make tables usable through responsive layouts, carefully selected columns or controlled horizontal scrolling where necessary.
- Ensure examinations, course materials, results and payment flows work on mobile browsers.
- Use comfortable touch targets.
- Prevent horizontal overflow.
- Avoid tiny text and cramped tables.
- Ensure all controls are easy to operate using touch.

Do not consider a page responsive merely because it technically fits on a phone.

The layout must be intentionally redesigned for the available screen size.

## 27.8. Interaction and motion

Use subtle, purposeful interactions.

Include:

- Clear hover states.
- Focus states.
- Active states.
- Selected states.
- Disabled states.
- Loading states.
- Smooth but restrained menu transitions.
- Useful dialog transitions.
- Clear feedback when an action succeeds or fails.
- Progress indicators where they help users understand a workflow.
- Skeleton loading states for data-heavy pages.

Do not animate every element.

Avoid distracting motion, unnecessary parallax and animations that interfere with usability.

Respect reduced-motion preferences.

- Excessive colours.
- Generic dashboard layouts reused for every role.

- Cramped layouts.
- Random decorative icons.
- Excessive shadows.

- Weak typography.
- Arbitrary font choices.
- Inconsistent spacing and alignment.

## 27.12. Required UI review workflow

Before considering any page complete:

1. Compare the page against the attached mockup's visual direction.
2. Check layout balance, spacing, typography, alignment and visual hierarchy.
3. Review the page at desktop, tablet and mobile widths.
4. Check all navigation, forms, buttons, menus, dialogs and interactive states.
5. Verify loading, empty, error, success and permission-denied states.
6. Check accessibility, keyboard interaction and readable contrast.
7. Remove generic or repetitive layouts.
8. Refine components that look unfinished or template-generated.
9. Ensure the page uses the shared design tokens and reusable components.
10. Confirm that the page is both visually polished and functionally complete.

Do not consider a page finished merely because it renders correctly.

It must also be visually polished, responsive, accessible and consistent with the overall product.

# 32. IMPORTANT IMPLEMENTATION RULES FOR ANTIGRAVITY

Follow these rules throughout development.

1. Inspect the existing project before creating or replacing files.
2. Maintain a clear project structure.
3. Build reusable frontend components.
4. Keep backend modules independent and modular.
5. Define database relationships before implementing dependent modules.
6. Use database migrations.
7. Never expose secrets or credentials.
8. Implement proper authorization on every protected backend endpoint.
9. Validate all user input.
10. Do not use mock API responses in production functionality.
11. Do not hardcode programmes, academic sessions, fees or grading scales.
12. Use actual database records throughout the application.
13. Ensure that every frontend feature has a corresponding backend implementation.
14. Do not leave unfinished buttons, forms or navigation links.
15. Do not silently remove existing working functionality when modifying code.
16. Run tests and resolve errors before marking a phase complete.
17. Document important architectural decisions.
18. Keep a development progress document showing completed modules, pending work and known issues.
19. Use realistic seed data only for local development and clearly separate it from production data.
20. Prioritize a reliable, maintainable application over rushing through the feature list.
21. Keep the supplied UI mockup available as a visual reference throughout frontend development and use it when reviewing desktop, tablet and mobile screens.

If a feature depends on an external provider, build the integration interface and configuration requirements, clearly document what credentials are needed, and do not pretend the integration is operational before it has been configured and tested.
